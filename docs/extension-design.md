# Chrome 扩展控制层

## 运行目标

目标岗位和城市可选，默认 AI Agent、北京；使用 BOSS 已有附件简历，启动后持续处理，关闭控制台停止，同岗位避免重复发送，未确认记录隔离后继续其他岗位。

## 选择

采用普通 Chrome + Manifest V3 扩展 + 本机 Node 服务。扩展通过标准 DOM 控件处理网页，不连接 DevTools，不调用 chrome.debugger、不改变网站检查、浏览器指纹或验证码。普通 Chrome 的本地扩展需要一次加载。技术可行不等于 BOSS 许可，也不能保证不限制账号。

保留 runner/store 的筛选、节奏、持久化意图和恢复接口。新 ExtensionBrowser 实现 open、openForLogin、login、discover、details、contact、close；旧 CDP 适配器保留为测试和诊断代码，不作为新的默认运行方式。

## 目标标题规则与候选处理

Node 配置使用 `roleTitleExclusions: [{targetRole, keywords}]` 保存各目标岗位的标题职能排除，默认 `[]`。目标名称按 Unicode NFKC、首尾空白清理、连续空白折叠、大小写归一后精确匹配，只应用当前目标的规则。最多保存 20 个不同目标，每项包含 1 至 50 个非空关键词，目标名及单个关键词最多 100 字符；控制台编辑当前目标时保留其他目标的规则，空输入移除当前项。

各目标可以单独保存标题职能排除规则；规则只匹配标题，不排除仅在职责中提到协作的岗位。通用软件不全局禁投产品岗位；现有 `excludeKeywords` 的字面含义保持一致。

共享 `precheckJob` 在读取详情前仅按已配置的标题规则、标题排除词及排除公司作明确拒绝，保存拒绝原因。列表缺少城市、标签或描述，或标题未包含目标关键词时，继续读取详情完成城市、岗位类型与职责校验。每个搜索词的候选按配置目标名及 `requiredAny` 在标题中的相关性稳定排序，同分保留原列表顺序；每个候选仍按 details → 验证 → contact 串行处理，避免为了排序预读所有详情再重新访问。

拒绝缓存保留 6 小时，筛选签名包含 `roleTitleExclusions`。记录同时保存列表 `cardFingerprint`，由标题、公司、城市和排序后的标签生成；筛选签名或列表指纹改变时缓存失效，标签顺序变化不单独触发失效。旧拒绝记录缺少指纹时重新核对一次。已联系去重、待发简历复查和 uncertain 跳过规则仍在候选处理前生效。

## 固定消息协议

Node ↔ 扩展使用 loopback HTTP 长轮询；仅 /bridge 路由接受经配对的扩展请求，不放宽现有控制台 API 的同源策略。配对秘密存于 data，权限 0600，不随源码分享；后台保存自己的扩展实例 ID。每次服务启动和任务开启使用新的 epoch，命令包含唯一 ID、截止时间、固定操作名称及结构化参数。

固定操作包括 OPEN_SESSION、READ_STATUS、INSPECT_PAGE、READ_CARDS、READ_DETAIL、NAV_SEARCH、NAV_JOB、NEXT_PAGE、STOP_SESSION，以及 READ_CONVERSATION、OPEN_CONTACT、READ_CONTACT_CONFIRMATION、DISMISS_CONTACT_CONFIRMATION、VERIFY_CONVERSATION_JOB、READ_CONVERSATION_VERIFICATION、FILL_GREETING、SEND_GREETING、READ_RESUME、REQUEST_RESUME、SELECT_RESUME、CONFIRM_RESUME。协议不接受任意脚本、函数、CSS 点击程序或私有网络 API 请求。

扩展仅访问 HTTPS www.zhipin.com 的顶层网页及 127.0.0.1 的本地服务。网页无 postMessage 桥；只有扩展自己的后台能向 content script 发指令，浏览器提供的 tab/frame/document/url 元数据须校验。一个任务只绑定一个扩展创建的工作标签；停止时只关闭该标签，保护用户原有标签。

NAV_SEARCH、NAV_JOB 在一次有效许可下启动 Chrome 跳转，立即返回目标地址确认，不在动作许可内等待网页加载。Node 严格核对这个地址，清理旧文档证据，再以轻量只读 READ_STATUS 等待指定官方页面；搜索城市和关键词必须各出现一次且精确匹配，详情路径必须包含同一岗位 ID。页面加载较慢不会延长发送许可；未确认目标时不会读取岗位或发送消息。OPEN_SESSION、NEXT_PAGE 和网页发送动作仍保持原有单次许可。

控制台的受保护 `/api/inspect` 只接受空对象，调用固定 INSPECT_PAGE，不接受脚本、选择器或其他操作。诊断只返回有限的卡片、详情元素和公开职位字段，整个结果限制 64 KiB，不读取表单值。职位页确认弹窗结构诊断限制为最多两个弹窗、四条消息及有限子元素，只记录标签、类名、文本长度与明确状态词，不返回招呼正文。

## 动作和结果

页面读取必须返回当前 URL、document nonce、风险状态。登录、验证码、频率提示和不支持事件立即暂停。岗位 ID、名称、公司必须得到确认；会话必须具有同一岗位的明确 ID 证据。未知或歧义页面不能发消息。

每个不可逆动作前，Node 先将 intent 原子保存，再签发一次命令。扩展执行前向 Node 申请仍有效的许可，并重新验证 document 和接收者。过期、断线或停止的命令不能执行；动作结果丢失转为 uncertain，不自动重发。浏览器或服务重启也不能重放发送动作。DOM 的合成事件若被网站拒绝则暂停，不能伪造 trusted 事件。

岗位页的“已发送”小弹窗只用于确认招呼。它必须出现在本次已获许可的打开沟通动作之后，且当前岗位、招聘者、公司和独立发送状态一致；不赋予附件发送权限。普通任务确认后先落盘，可以立即继续下一岗位并将附件加入待发队列。进入即时附件分支时，关闭同一弹窗，再通过原岗位的“继续沟通”进入已有会话，不重复打招呼。

“继续沟通”若整页导航导致内容脚本回执丢失或旧回执被新文档取代，仅在 `resumeOnly` 且原岗位已确认已有沟通时，读取当前页面观察是否已到官方聊天页；不重复点击、不推断新的招呼成功。进入聊天页后仍须以下岗位卡验证，验证码、错误岗位或仍停留详情页均不能继续附件步骤。新联系的丢失回执仍进入人工核对。

只读 READ_STATUS 与 INSPECT_PAGE 会重新向后台登记实际 Chrome 顶层文档来源与自身 nonce，恢复页面切换后丢失的映射。Chrome 原始消息来源地址与当前页面地址分别保存并精确校验，当前地址还须与浏览器实际地址及内容脚本的最终检查一致。旧动作回执只有仍属于原工作标签、原映射及相同 nonce 才能更新元信息，不能覆盖已到达的新文档登记。认证、任务和期限均有效的错误回执可直接报告拒绝原因；成功回执仍必须取得动作许可。显式诊断只返回上一条操作的固定名称、白名单错误码、耗时、预览数量和阶段，连同原诊断保持 64 KiB 上限。

官方聊天页若只有岗位名称和公司而没有岗位链接，不能凭名称发送附件。程序在唯一选中会话中核对名称、公司及招聘者后，点击其实际岗位卡；后台只跟踪该工作标签在原动作期限内新建且 `openerTabId` 一致的唯一预览标签。等待浏览器提交实际网址，精确匹配原岗位 ID 后，才对原聊天文档建立临时绑定。预先存在、来源未知、多个子标签、错误网址、文档切换均拒绝。证明令牌由扩展后台生成；内部绑定及撤销操作不向 Node 公开。失败或取消撤销旧绑定，撤销不能确认时拒绝该文档的后续发送，成功后仅清理自有临时预览。

附件步骤仍在同一绑定会话中重新确认控件。真实网页的“发简历”若带 `unable` 等禁用状态，即使原生无障碍报告可点击，也记录暂无法发送并等待复查。申请、同意、选择和附件送达分别持久化；达到附件公司目标后不再进入新的附件步骤。公司目标、未知动作预留及节奏细节见 [速度与数量目标](speed-and-goals.md)。

## 验收

先在本地真实 Chromium 页面验证固定操作、跨文档拒绝、错误收件人、重复/过期命令、断线停止与不确定结果。再在普通 Chrome 加载扩展，连接真实 BOSS，确认账号和岗位读取稳定。最后在已授权的目标岗位中核对招呼、附件申请及真实附件发送，严格区分三个状态。没有真实证据的阶段不得报告完成。
